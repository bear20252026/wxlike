## 2. PR #448 的 CI 红是怎么修的（供下次别再踩）

CI 是 fail-fast 的：`first-failing-step 掩盖后面的失败`在这条链路上发生了**两次**。

1. 第一层（`98df0678`）：relations governance.rs type_complexity + identity 模块文档链接私有项。
   本地只验证了已知的两个 crate → 推送后 CI 又揭出第二层。
2. 第二层（`ba4a4781`）：server mount_common.rs result_large_err（Box 化 + 12 调用点）、
   mini_runtime 文档链接 CatalogStore（同模块链接在 rustdoc 1.97 解析不到，改显式路径）、
   **schema 快照漂移**（G02-09 治理表落库但快照没重生成——CI fail-fast 在 platform 的
   schema_snapshot 上，**后面 server 的测试根本没跑到**）、
   **commerce 金额往返真 bug**（prepare 的 draft 原样回传 create 时 minor 串被当小数解析，
   差百倍，确认令牌 HMAC 必失配 → INVALID_SIGNATURE）、
   **三个后台面测试的进程级 env 竞态**（WXLIKE_ADMIN_TOKEN 并行 set/remove 互相污染
   对方刚 boot 的栈 → 合并为一个顺序测试）。

教训写死：**修 CI 红必须在本地跑全 workspace 的 clippy/doc + 受影响 crate 全套测试再推**，
不要推一次修一层。

  内存平台显式跳过镜像（留日志）；WS 泵/设备密钥联动只留痕，接入点在 server 层。
